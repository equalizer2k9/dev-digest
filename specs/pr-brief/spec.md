# Spec: PR Why + Risk Brief
Spec ID: SPEC-01
Status: approved
Supersedes: —

Source: `docs/hw5/requirements.md`; its criteria are referenced as `P<level>-<n>`.

## Problem and user

A reviewer opens someone else's pull request "cold": they do not know why the change exists, what in it
is risky, or which file to read first. Smart Diff and Blast radius answer part of this, but in separate
places, and nothing says "start here, because …". The user is a reviewer on the Overview tab of a pull
request. They need one block — the **PR Brief** — that says what the PR does and why, lists concrete risks
tied to files, and gives an ordered `file:line` reading list, without inventing files or lines.

## Goals / Non-goals

- G1. One PR Brief block on the Overview tab, generated on demand: summary, Risk areas, Review focus,
  shown together with the existing Blast radius block, and stating which inputs it lacked.
- G2. Every file and every Review focus line the brief names is one the system knows about.
- G3. One request to the model per generation; the model gets computed facts, never diff code.
- G4. The brief is stored, survives a reload, is marked stale when the PR head moves, and can be
  regenerated by the user.
- G5. A Review focus item or a risk's file reference opens that file, at that line, on Files changed.

Non-goals:

- NG1. PR intent and attached spec documents: the Intent Layer and the Project Context Folder do not
  exist in this fork; the brief works without them and says so.
- NG2. A verdict banner with PR score inside the brief (P3-1); workflow-retro and cost report (P3-7);
  homework delivery criteria (P1-7, P1-8, P2-1 to P2-3), which are not system behaviour.
- NG3. Using a linked issue as a fact, in any form.
- NG4. Sending diff hunk bodies, file contents or other source code to the model.
- NG5. Automatic generation (on import, page load, new commit, review run); more than one stored brief
  per PR; a stored snapshot of the blast radius; a PR history block.
- NG6. Asking the model again after an invalid reply; refusing a PR because it is too large.
- NG7. Showing the model call in the studio; posting the brief to GitHub; exposing it over MCP.
- NG8. Navigating from the brief to a file that is not in the PR's diff.
- NG9. Restoring a Files changed target from the page address on load; Back-to-Overview behaviour; an
  in-progress indicator that survives a page reload.
- NG10. Pixel parity with the prototype; a plain list layout is acceptable.

## User stories

- US-1. As a reviewer, I want to generate a brief from a PR's Overview tab — a summary, risks tied to
  files and an ordered `file:line` reading list — so that I know the purpose, the danger and where to start.
- US-2. As a reviewer, I want to click an entry and land on that file and line in Files changed.
- US-3. As a reviewer, I want the brief to persist and to tell me when it describes an older commit or
  lacked inputs, so that I neither wait again nor over-trust it.
- US-4. As a workspace owner, I want the brief to use the model I chose for Risk Brief in Settings.

## Acceptance criteria (EARS)

Definitions. The **allowed path set** is the paths of the PR's changed files plus the paths of the files
in its blast radius (files declaring a changed symbol, files of callers). The **known lines** of a file
are the new-side lines inside the line ranges of its diff hunk headers (changed file) and the lines of
its callers (blast radius caller file). Both come from the system's complete facts about the PR, never
from what was sent to the model.

Brief block
- AC-1 (P1-1). The system shall display a PR Brief block on the Overview tab of a pull request, with a
  "Generate brief" control WHILE no brief is stored for it.
- AC-2 (P1-1). WHEN the user activates "Generate brief", the system shall generate a brief and display
  it in the block without a page reload.
- AC-3 (P1-2). WHILE a brief is stored, the system shall display its summary, its Risk areas list and its
  Review focus list, with an explicit empty-state text in place of a list that is empty.
- AC-4 (P1-2). The system shall display the existing Blast radius block, computed live, on the Overview
  tab together with the PR Brief block.
- AC-5 (P1-2). WHILE a brief is displayed, the system shall state that no intent is available and that
  no specs are attached.
- AC-6 (P1-3). The system shall display each risk with its title, its severity (high, medium, low) and at
  least one file path, ordered by severity high to low and by model order within a severity.
- AC-7 (P1-3). The system shall display each Review focus item as `file:line` with its reason, in the
  order the model listed them.
- AC-8. The system shall store at most 7 risks and at most 5 Review focus items per brief — the first
  ones in display order that remain after AC-10 and AC-11.
- AC-9. The system shall offer generation and refresh for a pull request in any state (open, closed,
  merged); IF the pull request has no recorded changed files THEN it shall refuse with a message in the
  block and make no model call.

Grounding
- AC-10 (P1-4). The system shall remove from each risk every file reference outside the allowed path set
  and drop a risk that has no file reference left.
- AC-11 (P1-4). The system shall drop a Review focus item whose file is outside the allowed path set or
  whose line is not among the known lines of its file.
- AC-12 (P1-4). The system shall never store or display a path outside the allowed path set, applying
  AC-10 and AC-11 against the complete set and lines whatever was left out of the model input, and using
  whatever paths are available when the blast radius is degraded or unavailable.

Model call
- AC-13 (P2-4). WHEN a brief is generated, the system shall send exactly one request to the model
  provider, with no re-ask after an invalid reply.
- AC-14 (P2-5). The system shall keep the whole input of the model call at or below 8 000 tokens as
  counted by the server's tokenizer — reducing it by the priority set in the plan when it is over, never
  failing for size — and shall never include a diff hunk body in it.
- AC-15. The system shall give the model these facts: the PR title; the PR description when present; per
  changed file its path, added and removed line counts, Smart Diff role and hunk line ranges as numbers
  only; and, when a blast radius is available, its summary and the file and line of each caller.
- AC-16 (P2-6). The system shall store a brief only from a reply that validates against the brief
  contract (summary, risks, Review focus items of file + line + reason), which the API and the studio
  shall define with identical shape.
- AC-17 (P2-7). The system shall call the provider and model selected for "Risk Brief" in the workspace's
  Settings — the Settings default when none is selected, and a changed choice from the next generation.

Storage and staleness
- AC-18 (P1-6). WHEN a pull request page is loaded and a brief is stored, the system shall display it
  without a model call; a model call is made only on "Generate brief" or refresh.
- AC-19 (P2-8). The system shall keep at most one brief per pull request, stored with the head commit SHA
  the pull request page showed when the generation was requested.
- AC-20 (P2-8). WHILE the SHA stored with the brief differs from the head SHA the page shows, the system
  shall display a stale marker and keep displaying the stored brief.
- AC-21 (P1-6). WHILE a brief is displayed, the system shall display a refresh control; WHEN it is
  activated the system shall generate a new brief with one model call whether or not the brief is stale,
  and on success replace the stored brief and remove the stale marker.

Navigation and risk details
- AC-22 (P1-5, P2-9). WHEN the user clicks a Review focus item whose file is in the PR's diff, the system
  shall open Files changed with that file's diff expanded (expanding a collapsed role group) and the item's
  line scrolled into view and briefly highlighted.
- AC-23 (P3-3). WHEN the user clicks a file reference of a risk whose file is in the PR's diff, the system
  shall open Files changed with that file's diff expanded; IF there is no target line or the line is not
  shown for that file THEN it shall scroll to the top of that file's diff.
- AC-24 (P3-4). IF the file of a Review focus item or risk file reference is not in the PR's diff THEN
  the system shall show "File not in this PR's diff" inline on it and not navigate on click.
- AC-25 (P3-2). The system shall display each risk collapsed without its explanation; WHEN the user
  clicks the risk row outside a file reference, it shall toggle the explanation.

Feedback and access
- AC-26 (P3-5). WHILE a brief is being generated, the system shall display a skeleton in the block and
  disable the "Generate brief" and refresh controls.
- AC-27. WHILE the stored brief is being loaded, the system shall display a loading placeholder, not
  "Generate brief"; IF loading fails THEN it shall display an error state distinct from "no brief yet".
- AC-28. IF a generation fails THEN the system shall display an error message with a way to try again in
  the block, and keep displaying any previously stored brief.
- AC-29 (P3-6). The system shall take every label and static text of the block from the studio's `brief`
  message namespace.
- AC-30. IF a brief is requested or generated for a pull request outside the caller's workspace THEN the
  system shall respond that the pull request was not found.

## Edge cases

- EC-1. No PR description → generated from the remaining facts. No recorded files → AC-9.
- EC-2. Blast radius degraded or repository not indexed → AC-12; the Blast radius block keeps its marker.
- EC-3. An item points at a blast-radius caller file the PR does not change → kept if it passes AC-10 and
  AC-11 (a focus line must be a caller line), shown per AC-24.
- EC-4. A changed file has no textual diff (binary, too large) → no known lines, so focus items for it
  are dropped; a risk may still reference it and opens it at the top (AC-23).
- EC-5. Every risk and focus item fails grounding → stored with its summary and the empty states of AC-3.
- EC-6. Invalid model reply, or no API key for the selected provider → AC-28; no second request.
- EC-7. The PR head moves during a generation → stored with the SHA of AC-19, shown stale.
- EC-8. Two generations at once (two tabs) → AC-19 holds; the brief stored last is shown.
- EC-9. The page is reloaded during a generation → the block shows the stored state (NG9).
- EC-10. Known limitation: GitHub returns at most 100 changed files per PR; files beyond that are neither
  facts nor in the allowed path set. No work required.
- EC-11. Title, description or a path reads like instructions to the model → treated as data; the reply
  must still pass AC-16, AC-10 and AC-11.

## Non-functional requirements

- NFR-1. Cost: one generation = one provider request; a page load = zero model calls.
- NFR-2. Input budget 8 000 tokens for the whole input, by the system's own tokenizer count.
- NFR-3. Kept out of the model input: hunk bodies, file contents, findings, repository map, commit
  messages, issues, intent, specs, PR history, symbol and caller names.
- NFR-4. Model-produced text is displayed as plain text, never interpreted as markup.
- NFR-5. API keys and tokens never appear in a stored brief or in logs of the generation.
- NFR-6. A stored brief is readable when GitHub is unreachable; a generation always ends, in a stored
  brief or a visible failure.

## Untrusted inputs

PR title, PR description, changed file paths and blast radius caller file paths come from outside the
system's control. Each is **data, not instructions**: in the model input each is wrapped in delimiters
under an injection guard — the same treatment the diff and PR description get in review runs
(`reviewer-core/src/prompt.ts:16-33`). The model's reply is not trusted either: it is accepted only
through AC-16, AC-10 and AC-11 and shown as plain text (NFR-4).
