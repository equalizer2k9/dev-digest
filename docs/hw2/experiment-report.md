## Що знайшли прогони A (без скілів)

- **#10, Test Quality** — знахідок немає, вердикт approve. У summary агент перелічив, що тести
  покривають відсутній заголовок, секунди, пробіли, HTTP-дату й невалідне значення, і на цьому
  зупинився: порожній рядок, минулу дату й `'0'` він без скілів не згадав.
- **#9, API Contract** — CRITICAL `server/src/modules/pulls/routes.ts:304`: false positive (нижче).
  Саме перейменування поля як зміну контракту агент без скілів **не назвав**.

## Суть знахідок B

**#10 — Test Quality Reviewer**

- WARNING `server/src/modules/pulls/retry-after.ts:7` — «Missing test for empty-string branch
  (value === '')»: гілка `return null` для порожнього рядка після `trim` не виконується жодним
  тестом; пропонує `parseRetryAfter('')` і `parseRetryAfter('   ')`.
- WARNING `server/src/modules/pulls/retry-after.ts:17-18` — «Missing test for clamped-to-zero
  branch on past date»: у тернарнику `seconds > 0 ? seconds : 0` гілка `: 0` не покрита, бо жоден
  тест не дає дату раніше за `now`.
- WARNING `server/src/modules/pulls/retry-after.ts:12-13` — «Missing test for boundary input '0'»:
  найменше валідне значення секунд не перевірене.

Перші дві — непокриті гілки (скіл `uncovered-branches`), третя — межовий випадок (`edge-cases`).
Номери рядків зсунуті на один-два відносно файлу (порожній рядок — рядок 9, тернарник — 19,
регулярка — 11), але всі в межах зміненої функції, тож знахідки пройшли перевірку цитат.

## False positives

- **`server/src/modules/pulls/routes.ts:304`** — у прогонах A і B на #9. Агент стверджує, що
  `added_lines: f.additions` читає неіснуюче поле і відповідь містить `undefined`. Це хибно: у цій
  гілці `f` — рядок таблиці `pr_files`, де колонка й далі називається `additions` (схему БД PR не
  чіпає); typecheck гілки проходить. Модель сплутала рядок БД з DTO `PrFile`. У v2-прогоні була та
  сама помилка з діапазоном `routes.ts:255-307`. Знахідки лишились у базі як є, не прийняті й не
  відхилені; діяти за ними не треба.
- **Неточність усередині справжньої знахідки** — `breaking-change` у прогоні B пише, що ламаються
  «detail and list endpoints». Список PR віддає `PrMeta`, його зміна не зачіпає; ламається лише
  `GET /pulls/:id`.
- **Не false positive, але шум** — чотири CRITICAL на одному рядку `platform.ts:190` мають одну
  причину, тому score PR падає до 0.

Що з цим робити далі (не зроблено, щоб не змінювати умови експерименту): у `response-schema`
додати крок «перш ніж флагувати producer, визнач тип об'єкта-джерела — рядок БД чи DTO».

## Висновок

AC-18 виконано: без скілів API Contract Reviewer не назвав перейменування поля зміною контракту, а
з чотирма скілами повідомив про breaking change з точним `platform.ts:190`. AC-17 виконано на
третій версії тестового PR: без скілів Test Quality Reviewer схвалив тести, а зі скілами назвав
дві непокриті гілки й межове значення `'0'` з `file:line`. На двох попередніх версіях, де
непокритими були очевидні гілки, агент флагував покриття і без скілів — скіл вмикає знахідку лише
там, де прогалину не видно без явного переліку гілок і меж.
Обидва агенти дають один і той самий false positive на `routes.ts:304`, з якого видно, що скіли
додають правила, але не перевірку фактів.
