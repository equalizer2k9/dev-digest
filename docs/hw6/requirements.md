## Частина 1 — лаба: евали harness

| Команда (у `evals/`) | Рівень |

### Маршрутизація «яка зміна → який eval»

Таблиця — у `evals/README.md`; у CLAUDE.md — один рядок-вказівник у розділі Docs і рядок пакета `evals/` у таблиці Packages. CLAUDE.md — символьне посилання на AGENTS.md, бюджет ≤ 80 рядків: якщо не влазить — стиснути інший рядок, правил не вирізати.

| Зміна | Що запускати |
| --- | --- |
| `.claude/skills/<name>/**` | `pnpm eval:quality` + евали цього скіла, якщо є |
| `.claude/agents/<name>.md` | евали цього агента + workflow |
| `AGENTS.md` / `CLAUDE.md` у корені | workflow |
| кейс або суддя в `evals/` | повторна серія-база (стара база непорівнянна) |

### CI — `.github/workflows/evals.yml`

- Тригер — `pull_request` за шляхами `.claude/**`, `AGENTS.md`, `CLAUDE.md`, `evals/**`, сам workflow; плюс ручний запуск з вибором моделей.
- Визначення зачеплених наборів — `evals/scripts/ci-detect.mjs` з пакета; доповнити: зміна кореневого `AGENTS.md` = зміна CLAUDE.md (у нас CLAUDE.md — посилання на нього). Зміна без евалів — рядок `SKIP <name> (no evals)`, не падіння.
- Job `quality` — `eval:quality`, без секретів, **блокує**. Модельні jobs — звіт (`continue-on-error`), не гейт: коштують грошей і коливаються.
- `permissions: contents: read`; `concurrency` з `cancel-in-progress`; `timeout-minutes` на кожен job; 1 прогін на кейс у CI.
- Ключ — лише `OPENROUTER_API_KEY` в Actions Secrets. PR із форку секретів не отримує → модельні jobs пропускаються з поясненням; `pull_request_target` не використовувати.
- Перевірка: тестовий PR (не мерджити), що змінює один скіл з евалами, одного агента з евалами і AGENTS.md → видно, які jobs запустились і які пропущені.

## Частина 2 — ДЗ: Eval Pipeline для рев'ю-агента

Змінили системний промпт, модель чи прилінкований скіл агента → прогнали евали → цифрами видно, покращили чи зламали. Кейси — з ваших рішень accept/dismiss над реальними знахідками, вигадувати сценарії не треба.

**Процес — SDD з L05:** spec-creator → `specs/eval-pipeline/spec.md` → implementation-planner → `plan.md` → cross-model review → спека й план закомічені до коду → `/run-plan` (implementer-и → architecture-reviewer → security-reviewer → коло фіксів → plan-verifier). У тексті ДЗ шлях `specs/eval-pipeline.md`; у нас конвенція репо — тека фічі зі `spec.md` і `plan.md` (CLAUDE.md, Naming), в описі PR це зазначити.

### User stories

- Створити eval case з реальної знахідки одним кліком: прийнята → «має знайти X у file:line», відхилена → «НЕ має коментувати Y».
- Бачити всі кейси набору агента.
- Запустити прогін агента на всіх кейсах.
- Бачити recall / precision / citation accuracy прогону.
- Бачити історію прогонів і порівняти два поруч («старий промпт vs новий»).

### Що вже є у форку (знайдено в коді)

| Що | Деталі |
| --- | --- |
| Таблиці | `eval_cases`, `eval_runs` у `server/src/db/schema/eval.ts` — порожні, ніхто не читає й не пише. `eval_runs` зараз — рядок на один кейс (`case_id NOT NULL`) |
| Контракти | `EvalCase`, `EvalOwnerKind`, `EvalRun` (recall, precision, citation_accuracy, traces_passed/total, per_trace) у `contracts/knowledge.ts`; `EvalCaseInput`, `EvalRunRecord`, `EvalRunResult`, `EvalDashboard` у `contracts/eval-ci.ts` — обидві копії `vendor/shared`. Єдиний споживач — фікстура `EvalRun` у `server/test/contracts.test.ts` |
| Версії агента | `agent_versions` — знімок конфігурації (промпт, модель, скіли) на кожну зміну |
| Рішення над знахідкою | `findings.accepted_at` / `dismissed_at`; `POST` дії accept/dismiss (`modules/reviews/findings.ts`) |
| Рушій рев'ю | `reviewPullRequest` з reviewer-core (як у `run-executor.ts`); `groundFindings` повертає `kept` і `dropped` |
| Клієнт | `client/messages/en/eval.json` (повний набір підписів, не підключений), `shell.json` → `nav.eval`, `app-shell/helpers.ts` уже розпізнає `/eval`; бракує пункту в `client/src/vendor/ui/nav.ts`. `AgentEditor/constants.ts`: зараз вкладки Config · Skills · Context |

Чого нема: модуля `eval` у server, роутів, виконавця прогону, скорингу, кнопки «Turn into eval case», вкладки Evals в агенті, сторінки Eval Dashboard, порівняння прогонів, `verify:l06`.

### Рішення (прийняті — spec-creator їх не перепитує)

| # | Рішення | Чому |
| --- | --- | --- |
| R1 | Кейс — **заморожений вхід**: повний diff файла знахідки (усі hunks), шлях, назва й опис PR; очікування `{ type: must_find \| must_not_flag, file, start_line, end_line, title }`; посилання на знахідку-джерело | PR потім змінюється — без заморозки прогони двох версій агента непорівнянні. Diff одного файла, а не всього PR, — щоб precision не розмивали знахідки в чужих файлах |
| R2 | Тип очікування — з рішення: accepted → `must_find`, dismissed → `must_not_flag`; знахідка без рішення — кнопка неактивна з підказкою; повторний клік по тій самій знахідці не створює дубль | так у ДЗ; дубль спотворить метрики |
| R3 | Знахідка з PR без тексту patch (сид #482) → відмова з поясненням | очікування не перетнеться з жодним рядком diff |
| R4 | Прогін агента бачить лише свою версію (промпт, модель, скіли) + заморожений вхід кейса; без intent, blast radius, конвенцій, Project Context, пам'яті | ці входи змінюються в часі — прогін перестав би бути відтворюваним |
| R5 | Той самий рушій reviewer-core з grounding gate, один виклик моделі на кейс; reviewer-core не змінюємо | евал має міряти те саме, що працює в продукті |
| R6 | Скоринг — лише кодом, жодного виклику моделі. Збіг = той самий файл + перетин діапазонів рядків | ДЗ прямо забороняє LLM-суддю тут; очікування — `file:line` |
| R7 | recall = must_find, для яких є ≥1 збіг / усі must_find прогону | «не пропускає» |
| R8 | precision = 1 − (знахідки, що влучили в зону must_not_flag) / (усі знахідки прогону після grounding) | «не шумить»; знахідки поза розміченими зонами не штрафуються — розмітки на них нема |
| R9 | citation accuracy = знахідки, що пройшли grounding gate / усі знахідки моделі; правило валідності цитати — лише з gate, без власної копії | «не галюцинує»; у збігах і precision враховуємо лише знахідки після gate — одна помилка не рахується двічі |
| R10 | Знаменник 0 → метрика «n/a», не 0 і не 1 | агент, що мовчить, не має precision 1.0 |
| R11 | Кейс пройдено: must_find — ≥1 збіг; must_not_flag — жодного збігу | лічильник «N/M passed» |
| R12 | Прогін = рядок набору: агент, версія агента, модель, статус, час, метрики, вартість, результати по кейсах (`eval_runs` переробити під це; зміна схеми — лише через `db/schema` + `pnpm db:generate`) | порівняння двох прогонів = два рядки; історія = список рядків |
| R13 | Прогін — лише явною дією користувача, у фоні, клієнт опитує статус; один активний прогін на агента; помилка одного кейса не валить прогін | відкрити вкладку — нічого не коштує |
| R14 | Порівняння рівно двох прогонів: дельти recall / precision / citation / вартості, які кейси змінили статус, diff системного промпта між версіями агента (з `agent_versions`) | «старий промпт vs новий» |
| R15 | Заморожений diff і опис PR — недовірені дані, як у рев'ю (`wrapUntrusted`); усі роути в межах workspace | кейс несе чужий текст у промпт |
| R16 | Контракти — розширити наявні `Eval*` в обох копіях `vendor/shared`, без нового розходження; тест на паритет двох копій | дві копії вже розійшлись у 5 файлах |
| R17 | `verify:l06` — скрипт у `server/package.json`: тести скорингу, створення кейса (заморожений вхід), паритету контрактів, інтеграційні тести роутів і меж workspace (без Docker — пропускаються, як інші `*.it.test.ts`). Запуск: `cd server && pnpm verify:l06` | у форку такого скрипта нема, ДЗ вимагає зеленого |

### Дані й експеримент для демо

1. Набір ≥ 8 кейсів для одного агента (той, у кого найбільше рішень accept/dismiss на PR з реальним diff), обидва типи. Бракує рішень — прогнати рев'ю на тестових PR і розмітити знахідки (рішення приймає користувач).
2. Прогін на поточному промпті (v1) → покращений промпт (v2, закриває пропущений must_find) → прогін → Compare: метрики видимо рухаються.
3. Зіпсований промпт (v3: «познач кожне стильове зауваження, невикористаний імпорт і назву як WARNING») → прогін → precision падає на кейсах must_not_flag → Compare v2 ↔ v3 → повернути v2.

### Критерії ДЗ

| № | Критерій |
| --- | --- |
| 1 | У наборі ≥ 8 кейсів |
| 2 | Кейс створюється зі знахідки одним кліком; обидва типи (must_find / must_not_flag) працюють |
| 3 | Зміна системного промпта видимо рухає recall / precision між двома прогонами |
| 4 | Скоринг не робить жодного виклику моделі |
| 5 | `pnpm verify:l06` зелений |

Чек-лист здачі: спека в `specs/` · `verify:l06` зелений · скріншот порівняння двох прогонів з різними промптами · **відео обов'язкове**, розповісти що і чому (замінює текстовий звіт). Форма здачі — посилання + файл до 150 МБ.

Що цінує ментор (з попередніх ДЗ): лаба — частина здачі; кожен етап конвеєра — свій агент; звіти рев'юерів і plan-verifier у `docs/hw6/`; один PR; чесна деградація з записом у лог.

### Сценарій відео (1–3 хв, титри «що і чому»)

1. PR → прийнята знахідка → «Turn into eval case»; відхилена → те саме (must_not_flag).
2. Агент → Evals: набір ≥ 8 кейсів → Run eval → метрики v1.
3. Змінити промпт (v2) → Run eval → Compare v1 ↔ v2: дельти, diff промпта.
4. Зіпсувати промпт (v3) → Run eval → precision падає → Compare.
5. Eval Dashboard.
6. Коротко: лаба — `evals/` (eval:quality, A/B серіями, workflow-трейс), CI-прогін на тестовому PR.
7. Титр: «Очікування — file:line, тому скоринг рахує код, а не модель: дешево, детерміновано, без судді, якого теж треба було б перевіряти».
