  нас заведено». Очікування — 422 від глобального обробника, тест на 422, узгодженість коду, тестів

## Що видно з виходів (ручний перегляд)

1. **Загальний скіл тягне проти конвенції репо.** `with_skill/run-1` задачі 2 прибрав
   валідацію з `schema.body` у handler: `CreateEvalCaseFromFindingInput.safeParse(req.body ?? {})` і
   `reply.code(400).send({ error, issues })`. У NOTES він посилається на правило скіла
   `parse-use-safeparse`. Це порушує onion-правило 7 («validation at the boundary only… never
   `Schema.parse(req.body)` inside a handler»), а форма помилки `{ error, issues }` не збігається зі
   стандартною `{ error: { code, message, details } }`. Скіл `zod` — загальний, про наш репо він не
   знає.
2. **400 проти 422 — ніхто не тримає узгодженості.** `with_skill/run-2` пише в NOTES «Invalid
   request bodies return 422», а в тесті перевіряє `toBe(400)` — сам собі суперечить.
   `without_skill/run-1` стверджує «ZodTypeProvider automatically returns 400», а його тести «returns
   400» не викликають `app.inject` взагалі. Найближче до правди — `without_skill/run-2`: тести
   перевіряють 422, але handler дублює `.parse` поверх `schema.body`.
3. **Чиста користь скіла — вузька.** Лише один прогін зі скілом пояснив різницю `z.input` / `z.infer`
   для `enabled` з дефолтом. Обидва прогони зі скілом не додали `refine` на діапазон рядків. Один
   забув експорт у barrel — і програв сліпе порівняння.

Grader окремо покритикував самі очікування: розділити 2.3 на «помітив 422» і «явно обрав статус і
сказав про це»; у 2.4 вимагати відповідь саме з `app.inject`; додати перевірку, що `schema.body` не
дублюється `.parse` у handler, і що NOTES не суперечать тестам. Режим «лише вимірюємо», тож
очікування не змінювались.

## Що Skill Creator не покриває порівняно з `evals/`

| Що | Skill Creator | `evals/` |
|---|---|---|
| Активація скіла в живій сесії | Ні: прогін «зі скілом» отримує інструкцію прочитати SKILL.md, тобто вимірюється зміст, а не те, чи модель сама вибере скіл з-поміж усіх. Оптимізатор опису (`run_loop`) перевіряє тригер через `claude -p` на синтетичних запитах, без нашого AGENTS.md | `activation`-кейси workflow: фактичний виклик `Skill` або читання SKILL.md у сесії з `settingSources: ["project"]`, з негативним контролем |
| Виклик субагента | Немає поняття агента чи dispatch | `dispatch`-кейс: у трейсі є `Agent` → `architecture-reviewer` |
| Вплив AGENTS.md | Обидві конфігурації отримують той самий контекст проєкту; контролю без нього нема | `contrast`: репо проти порожньої теки — чи прочитано файл, на який вказує AGENTS.md |
| Перевірка плану (Plan Verifier) | Немає: лише очікування до виходу одного запиту, без плану чи AC. Код не збирався й не тестувався — у worktree виконавців нема `node_modules` | Не в `evals/` — це агент `plan-verifier` з конвеєра `/run-plan` |
| Серії й регресії | Одна ітерація без міток версій; час і токени — лише з повідомлень про завершення субагента (пропустиш — втрачено); скрипт записав `runs_per_configuration: 3` при 2 прогонах, довелось виправити | `eval:repeat --label` + `eval:delta`, `records.jsonl`, CI |

Що в Skill Creator сильніше: сліпе порівняння з рубрикою, переглядач виходів для людини, grader,
який критикує самі очікування.
