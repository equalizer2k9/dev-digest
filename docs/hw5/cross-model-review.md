## Чекліст, який отримала модель

1. Покриття: кожен AC має задачу і названий тест.
2. Суперечності з кодом або правилами репозиторію (`AGENTS.md`).
3. Зайва складність: задачі, абстракції, поля, яких не вимагає жоден AC.
4. Безпека: заголовок і опис PR як недовірені дані в промпті, рендер відповіді моделі, шляхи з відповіді в навігації, секрети, логи.
5. Порядок задач і ризики.

## Що приймаємо і чому

**F-1 — прийнято.** Знахідка точна: у плані `get` сервісу не мав перевірки існування PR, тож 404 з AC-30 на `GET` не мав звідки взятися. Тепер `BriefService.get` спершу робить workspace-scoped `reviewRepo.getPull` (немає → 404) і лише потім читає рядок. Додано unit-тест у T-5: для чужого PR — `NotFoundError`, репозиторій брифу не викликається.

**F-2 — прийнято частково.** Заголовок PR справді нічим не обмежений, тож додано шостий крок скорочення — обрізання хвоста заголовка з `…` — і тест у T-4 із заголовком, який сам перевищує бюджет. Частину про blast summary не приймаємо: `buildSummary` (`server/src/modules/blast/helpers.ts:31-38`) складає рядок із чотирьох лічильників (`2 symbols · 14 callers · 3 endpoints · 1 cron`), він обмежений за побудовою. Інструкції фіксовані й уже мають тест «до 1 500 токенів».

**F-4 — прийнято.** Обгортка `wrapUntrusted` застосовується до всіх чотирьох блоків, але тест доводив це лише для опису. Тест у T-4 став параметризованим: заголовок, опис, шлях зміненого файла, шлях викликача — значення з `</untrusted>` та рядком-«інструкцією» лишається у своєму блоці, роздільників рівно по одному на блок.

**F-7 — прийнято.** Дешева перевірка проти подвійного POST: «Try again» блокується під час генерації, у T-8 додано тест на стан «помилка + генерація».

## Що не приймаємо і чому

**F-3 — не приймаємо (рішення власника спеки).** `intent` і `history` лишаються nullable у `PrBrief`: це поля контракту стартера, їх заповнять Intent Layer та історія PR, тож форма збереженого JSON не зміниться. `null` дає UI показати «intent недоступний» з даних, а не з припущення в коді (AC-5). Модель цих полів не бачить і не пише: її відповідь валідовується окремою `PrBriefDraft`.

**F-5 — не приймаємо.** Перевірено в коді: `buildSummary` приймає лише чотири числа і повертає лише лічильники, імен символів чи викликачів у рядку бути не може. Модель не мала доступу до коду й чесно позначила це як неперевірене. Окремий «агрегатний» summary для брифу був би дублюванням.

**F-6 — не приймаємо.** Таблиця Naming описує максимальну форму модуля. Фактично з дванадцяти модулів каталог `repository/` має лише `reviews` (кілька сутностей); `agents`, `conventions`, `pulls`, `repos`, `skills`, `repo-intel` тримають один `repository.ts`. Модуль `brief` має одну сутність (`pr_brief`), тож один файл відповідає усталеній практиці.

## Обмеження цього рев'ю

- Модель бачила лише три документи, без коду. Знахідки про код (F-5, F-6) вона сформулювала як припущення; їх перевірено вручну проти репозиторію.
- Один прогін однієї моделі; повторний прогін після правок плану не робився.
- Після рев'ю план змінено рішенням власника: T-2 зведено до експорту `INJECTION_GUARD`, LLM-провайдери не чіпаються — re-ask вимикає `maxRetries: 0`, мережеві повтори при 429/5xx лишаються як у рев'ю (відоме обмеження); ціль файл/рядок більше не пишеться в URL (AC-22). Ці зміни модель не бачила.
